# 아키텍처 설계 순서 (설계 문서의 기본기)

- 용도: 설계 문서를 쓸 때 장 순서와 빠뜨리기 쉬운 기본 항목. 일반 소프트웨어 아키텍처 지식을 정리한 것이며 사내 방법론 `A1_방법론.md` 와 별개
- 규칙: 각 단계에서 고른 방식과 이유를 한 줄씩 적음 (고르지 않은 방식은 쓰지 않음)

## 1. 순서
| 단계 | 정하는 것 | 문서 장 | 엔진 |
|---|---|---|---|
| 1 사용자 흐름 | 사용자가 목표(가입, 검색, 결제, 수집 확인 등)까지 화면에서 거치는 행동과 이동 경로. 이후 모든 선택의 기준 | 사용자 흐름 장 | `mermaid` flowchart, `chevrons` |
| 2 시퀀스 | 행동 하나를 처리하려고 내부 구성요소가 어떤 순서로 호출되나 | 처리 순서 장 | `mermaid` sequenceDiagram |
| 3 시스템 구조와 배치 | 서버와 장치를 어떤 단위로 나누고 어디에 배포하나 | 배치도 장 | `DocGrid` (읽힘 규칙 참조) |
| 4 데이터와 제어 흐름 | 값과 실행 권한이 어떤 방식으로 흐르나 | 구성도 선 규칙과 흐름 설명 | `link`, 범례 |
| 5 내부 코드 구조 | 한 프로그램 안을 어떤 계층과 규칙으로 나누나 | 기능 구조 장 | `Col.table`, `chip_tree` |

## 2. 사용자 흐름이 구조를 정함
- 정보 조회 위주는 캐싱, 정적 구성, 단일 배포 단위
- 실시간 상호작용 위주는 이벤트 주도, 웹소켓
- 복잡한 거래(결제, 주문) 위주는 서비스 분리, 분산 거래 관리

## 3. 시스템 구조 선택지
| 방식 | 특징 | 한계 |
|---|---|---|
| 단일 배포 (모노리식) | 한 프로젝트, 한 배포 단위. 초기 개발이 빠름 | 커지면 유지보수와 부분 확장이 어려움 |
| 서비스 분리 (MSA) | 독립 배포 가능한 작은 서비스. 확장과 기술 독립 | 분산 관리와 데이터 정합성이 까다로움 |
| SOA | 서비스 단위에 중앙 미들웨어(ESB) 로 통신 | 공유 DB 가 많아 서비스 간 결합이 높음 |
| 클라이언트와 서버 | 화면과 요청은 클라이언트, 데이터와 로직은 서버 | 기본 구조 |

## 4. 흐름 방식 선택지
| 방식 | 흐름 | 쓰임 |
|---|---|---|
| 요청과 응답 | 동기 호출 후 대기 | 일반 REST API |
| 이벤트 주도 | 발행과 구독으로 비동기 전파 | 시스템 간 결합을 낮출 때 |
| 파이프와 필터 | 데이터 흐름을 가공 단계에 차례로 통과 | 변환 파이프라인 |
| 배치 순차 | 이전 단계가 모두 끝난 뒤 다음 단계 | 야간 집계 |
| 단방향 흐름 | 동작, 상태 변경, 화면 반영 순으로만 | 화면 상태 추적 |
| 읽기와 쓰기 분리 (CQRS) | 변경 경로와 조회 경로를 나눔 | 조회가 많은 대규모 트래픽 |

## 5. 내부 코드 구조 선택지
| 방식 | 특징 |
|---|---|
| 계층형 | 화면, 응용, 비즈니스, 데이터 접근으로 수평 분할. 단순하지만 아래 계층에 의존하기 쉬움 |
| 포트와 어댑터 (헥사고날) | 핵심 로직을 중앙에 두고 외부(DB, API, 화면)와는 인터페이스로만 소통 |
| 클린 아키텍처 | 의존성이 바깥에서 안쪽(핵심 도메인)으로만 향함 |
| 모델, 화면, 제어 분리 (MVC 계열) | 화면이 있는 앱에서 역할 분리 |
| 마이크로커널 | 최소 핵심과 플러그인으로 확장 |

## 6. 설계 문서에 적을 것
1. 사용자 흐름 (누가 어떤 목표를 어떤 순서로 달성하나)
2. 핵심 처리 시퀀스 (한 사건 처리 순서)
3. 배치도와 기능과 배치 대응표 (`구성도_읽힘_규칙.md`)
4. 흐름 방식과 선택 이유 한 줄
5. 내부 구조(계층 또는 모듈)와 선택 이유 한 줄
